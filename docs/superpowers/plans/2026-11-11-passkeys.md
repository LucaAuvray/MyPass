# Clés d'accès via l'extension — plan d'implémentation

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal :** MyPass crée et utilise des clés d'accès (WebAuthn ES256) pour les sites ouverts dans Chrome/Edge, via les actions `passkeys-register` / `passkeys-get` de l'extension MyPass Browser, rangées dans le coffre au format KeePassXC.

**Architecture :** nouveau module `src-tauri/src/passkeys/` : `webauthn.rs` (crypto et encodage, pur), `options.rs` (validation des options reçues), `vault.rs` (champs `KPEX_PASSKEY_*`), `confirm.rs` (fenêtre de confirmation par événement Tauri), `mod.rs` (orchestration `register` / `get`). `native_messaging.rs` route les deux actions, chacune sur son propre fil. Côté front : une fenêtre de confirmation calquée sur `SshSignRequestDialog`, plus un badge. Côté extension : une seule ligne (`triggerUnlock`).

**Tech Stack :** Rust (`p256` 0.13, `sha2`, `base64`, `url`, `serde_json`), Tauri v2 (événements + commande), React 19 + react-i18next, extension KeePassXC-Browser 1.10.3 adaptée.

**Spec :** `docs/superpowers/specs/2026-11-11-passkeys-design.md`. Référence de protocole : KeePassXC 2.7.10, `src/browser/` (`BrowserAction.cpp`, `BrowserService.cpp`, `BrowserPasskeys.cpp`, `BrowserPasskeysClient.cpp`), lisible par `gh api "repos/keepassxreboot/keepassxc/contents/src/browser/<fichier>?ref=2.7.10" -H "Accept: application/vnd.github.raw"`.

## Global Constraints

- Algorithme : ES256 (`alg` = `-7`) uniquement. Attestation toujours `none`. AAGUID = 16 octets nuls. Compteur de signature = 0.
- Drapeaux de `authenticatorData` : `0x45` (UP|UV|AT) à l'enregistrement, `0x05` (UP|UV) à la connexion. Pas d'extensions (pas de drapeau ED), `clientExtensionResults: {}`.
- base64url **sans remplissage** pour tout ce qu'on émet ; en lecture, accepter aussi le remplissage et l'alphabet standard (entrées importées de KeePassXC).
- Champs d'entrée, noms exacts : `KPEX_PASSKEY_USERNAME`, `KPEX_PASSKEY_RELYING_PARTY` (non protégés) ; `KPEX_PASSKEY_CREDENTIAL_ID`, `KPEX_PASSKEY_PRIVATE_KEY_PEM`, `KPEX_PASSKEY_USER_HANDLE` (protégés, `Protected="True"`). Clé privée en PKCS#8 PEM (`-----BEGIN PRIVATE KEY-----`).
- Codes d'erreur (dans `response.errorCode`, nombre) : 20 ATTESTATION_NOT_SUPPORTED, 21 CREDENTIAL_IS_EXCLUDED, 24 EMPTY_PUBLIC_KEY, 25 INVALID_URL_PROVIDED, 27 DOMAIN_IS_NOT_VALID, 28 DOMAIN_RPID_MISMATCH, 29 NO_SUPPORTED_ALGORITHMS, 31 UNKNOWN_ERROR, 32 INVALID_CHALLENGE, 33 INVALID_USER_ID. Navigateur non associé : `error_response(req, 8, …)` en clair (ASSOCIATION_FAILED de KeePassXC).
- « Aucune clé pour ce site » et « annulé / délai dépassé » : réponse `success: "true"` **sans** clé `response` (repli silencieux sur Windows).
- Délai de confirmation : `timeout` des options en ms, borné à [15 s, 120 s], 120 s si absent.
- Le mutex `DbState` n'est **jamais** tenu pendant la confirmation. La clé privée n'est jamais loguée, ni envoyée au front, ni copiée hors du coffre pendant l'attente.
- Une seule nouvelle dépendance : `p256 = { version = "0.13", features = ["ecdsa", "pkcs8", "pem"] }` dans `src-tauri/Cargo.toml` (0.13.2 est déjà dans `Cargo.lock` via `ssh-key`).
- Chaînes utilisateur en EN + FR dans `src/i18n/{en,fr}.json`, aucune en dur ; le français vouvoie.
- Code, identifiants et commits en anglais, courts. Ne pas pousser sans l'accord de Luca.

## Review Focus

1. **Le coffre se verrouille (auto-verrouillage) pendant que la fenêtre de confirmation est ouverte** → aucune clé n'est renvoyée au site (sinon le site enregistre une clé que le coffre n'a pas). Test : Task 4, `vault_locked_during_confirmation_returns_no_credential`.
2. **La synchro ou Luca supprime l'entrée entre la question et la réponse** → la connexion échoue proprement, pas de panique ni de signature avec une clé périmée. Test : Task 4, `entry_deleted_during_confirmation_returns_no_credential`.
3. **Entrée importée de KeePassXC avec un identifiant en base64 standard rempli (`AQI=`)** → elle est trouvée et comparée sur les octets. Test : Task 3, `find_for_rp_matches_rp_exactly_and_decodes_ids`.
4. **`rp.id` en majuscules ou avec un point final (`BINANCE.com`, `binance.com.`)** → majuscules acceptées après passage en minuscules, point final refusé (28). Test : Task 2, `rp_id_rules`.
5. **Deux demandes simultanées (deux onglets) ou une demande pendant qu'un autre onglet remplit un mot de passe** → les fenêtres passent l'une après l'autre (file FIFO) et le remplissage des autres onglets n'attend pas. fn authenticator_data_layout() {

fn signature_verifies_over_auth_data_and_client_data_hash() {

    let auth = authenticator_data("binance.com", None);

fn sample() -> NewPasskey<'static> {
    NewPasskey { rp_id: "binance.com", rp_name: "Binance", origin: "https://accounts.binance.com",
        username: "luca@example.com", credential_id: "AQID", user_handle: "dXNlcjE",

fn protected(e: &Entry, k: &str) -> Option<String> {
    e.strings.iter().find(|s| s.key == k).and_then(|s| s.value.protected.clone())
}

#[test]
fn upsert_creates_dedicated_entry_with_protected_fields() {
    let mut kf = KeePassFile::new("t");
    let (uuid, replaced) = upsert(&mut kf, &sample());
    assert!(!replaced);
    let e = kf.root.group.entries.iter().find(|e| e.uuid == uuid).unwrap();
    assert_eq!((e.title(), e.username(), e.password(), e.url()),
               ("Binance", "luca@example.com", "", "https://accounts.binance.com"));
    for k in ["KPEX_PASSKEY_CREDENTIAL_ID", "KPEX_PASSKEY_PRIVATE_KEY_PEM", "KPEX_PASSKEY_USER_HANDLE"] {
        assert_eq!(protected(e, k).as_deref(), Some("True"), "{k}");
    }
    assert_eq!(e.get_field("KPEX_PASSKEY_RELYING_PARTY"), Some("binance.com"));
    assert_eq!(e.get_field("KPEX_PASSKEY_USERNAME"), Some("luca@example.com"));
    assert!(has_passkey(e));
}
